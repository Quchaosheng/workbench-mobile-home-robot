# ADR-0010: Runtime assurance is a track on this runtime, not a certification

Status: **proposed** (Assurance Track v1; requires Runtime, Safety, Motion and
Release owner review before any fault-injection code lands — see
[Approval register](#approval-register)). Until every owner records `approved`,
this record grants no safety, certification, release or procurement authority.

Date: 2026-10-25

Supersedes nothing. It extends [ADR-0006](ADR-0006-scenario-registry-contract.md)
and [ADR-0009](ADR-0009-run-resource-lifecycle-boundaries.md): ADR-0006 decides
how a scenario reaches the runtime and ADR-0009 decides who owns a resource while
it is there. This record decides what the repository is allowed to *claim* about
the runtime while it executes — and, more importantly, what it is not.

## Context

The runtime already has the pieces a reviewer would expect: bounded semantic
actions behind a policy validator, a controller that preempts on STOP and
cancel, a CAN device runtime that refuses late and uncorrelated acknowledgements,
a run-level timeout that publishes `TIMED_OUT` and deletes its staging
directory, a verifier that answers `confirmed` / `refuted` /
`insufficient_evidence`, and replay with event-stream and provenance hashes.

Those pieces are individually tested. What did not exist is one place that says
*which invariants the runtime is claimed to hold*, *where each one is enforced*,
and *what must happen when a named fault is injected*. Without that, every new
fault fixture re-argues the same questions, and a claim can be weakened by
deleting a test without anyone noticing.

The failure this record exists to prevent is a specific kind of overclaim. It is
easy and tempting to describe the result as a "robot safety certification
system". That description would be false: this repository has no hazard analysis,
no safety integrity target, no certified development process, no physical
evidence, and no assessment body. What it has is runtime assurance and acceptance
evidence. Naming the track honestly is the whole point of writing this down.

## Decision

1. **The project positions itself as task runtime *and* assurance**, not as a
   safety certification product. The English positioning is "Mobile Home Robot
   Task Runtime and Assurance"; the repository name does not change.

2. **The assurance layer is a track over the existing runtime, not a second
   runtime.** It may not introduce a second task state machine, a second policy
   validator or a second stop path. It reads what the runtime emits.

3. **A claim is only a claim if it resolves.** Every invariant in
   `docs/assurance/invariants-v1.json` names a `path.py::symbol` enforcement point
   and at least one committed test. An invariant with neither is recorded as
   `NOT_IMPLEMENTED` with a stated gap — visible, not silent.

4. **A fault never becomes a completion.** In
   `docs/assurance/acceptance-matrix-v1.json`, only the nominal case may expect a
   `confirmed` verdict. Every injected fault must expect `insufficient_evidence`
   or `refuted`, and must name the terminal state it has to reach.

5. **Coverage never inflates.** `SIMULATED`, `HARDWARE_TESTED` and
   `NOT_EXECUTED` are the only classes. A scripted or unit-level fixture is
   `SIMULATED` forever; nothing in this track is physical evidence.

6. **No certification language.** No row, page or report generated by this track
   may claim SIL, ASIL, ISO 26262, IEC 61508 or "certified". The gate refuses a
   `confirmed` verdict on a fault case and the generated page states the boundary
   in its own words.

7. **The register is gated.** `make assurance-check` fails when a claim no longer
   resolves, when a status inflates, when a required fault has no acceptance case,
   or when the generated page is stale.

## Consolidation map

The sibling repositories are not copied wholesale into this one. Each keeps one
owner and one direction of dependency:

| Repository | What it contributes | Where it lands | What it may not do |
| --- | --- | --- | --- |
| `embodied-agent-runtime` | Task event contract and runtime monitor semantics | `integrations/ros2_runtime/` as a typed adapter; the Python `ExecutionController` stays the only state machine | Duplicate cancel, STOP or device-ACK semantics |
| `ros2-control-vcan-motor-demo` | ros2_control hardware interface, virtual CAN, watchdog stop | `reference_robot/` as a test fixture, consumed through the device runtime boundary | Own a second safety path or a second CAN protocol |
| `RoboTraceOpt` | Latency and trace diagnosis | Stays independent; its `events.ndjson`, `trace.json` and `latency-report.json` are read as acceptance evidence | Become an execution dependency |
| `Quard-Star` | RISC-V, OpenSBI and FreeRTOS evidence | Frozen; remains its own repository | Be described as part of this product loop |

Moving code across those lines is a separate bounded slice with its own Task
Packet. This record only fixes the direction, so the same state machine is not
maintained twice.

## Consequences

- A reviewer can see, in one page, which invariants are enforced, which are gaps,
  and which test proves each claim.
- Adding a fault case means adding a row and a test, not writing a new fixture
  harness — the gate refuses a row whose evidence does not resolve.
- The repository will look *less* complete than a marketing claim, because gaps
  such as resource-claim exclusivity are printed rather than hidden.
- The first implementation slice (this ADR's Issue) ships the register, the
  matrix and the gate only. It adds one admission guard to `run_scenario`
  (refusing an unresolvable scenario before a runner starts) and no other runtime
  behaviour.
